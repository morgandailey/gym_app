# Android App 化流程架構圖

## 這份文件的目的

這份文件專門回答一個問題：

> 這個專案如果不以上架為前提，要怎麼一步一步變成在自己 Android 手機上像 App 一樣使用的產品？

這份文件不負責：

- 專案總覽
- 所有文件的入口整理
- 細部開發實作

那些內容應該回到 [README.md](./README.md)。

## 這份文件適合什麼時候看

當你要討論下面這些問題時，應該看這份：

- 先做 PWA 還是先包 Android
- 目前最合理的演進順序是什麼
- 如果不上架，最務實的做法是什麼
- 哪些事情現在不該做

## 這份文件和其他文件的關係

- 上層入口： [README.md](./README.md)
- 這份文件角色：負責「App 化方向與流程架構」

---

這份文件的目的不是討論上架，也不是現在就開始寫程式，而是先把方向釐清：

> 目標是讓這個專案在你自己的 Android 手機上，能夠「像 App 一樣使用」。

目前先不追求：

- Google Play 上架
- 多人使用
- 帳號系統
- 雲端後端
- 完整原生 Android 重寫

我們只聚焦在最實際的目標：

- 點一個 App 圖示就能開
- 在手機上穩定使用
- 能保存資料
- 訓練流程順手
- 不需要每次都像打開普通網頁那樣使用

---

## 一句話結論

對這個專案最務實的方向不是立刻重寫 Android，而是：

`先整理現有 Web 工具 → 做成更像 App 的安裝型版本 → 再決定是否需要 Android 容器包裝`

補充一個目前已確定的產品決策：

- `匯入訓練紀錄` 不再是日常主流程
- `本機歷史延續` 才是未來 App 化後的標準體驗
- `匯出` 保留作為備份與搬移用途

## 整體路線圖

```text
現在的狀態
  ↓
單檔 HTML 訓練工具
  ↓
釐清核心使用流程
  ↓
整理成可維護的 Web App 結構
  ↓
做成「手機上可安裝、可離線、可持久使用」的版本
  ↓
判斷是否已經足夠像 App
  ├─ 如果夠用：維持 Web App / PWA 路線
  └─ 如果不夠：再包成 Android App 容器
        ↓
   在自己手機安裝 APK
        ↓
   持續優化使用體驗
```

## 你真正要做的不是「開發 Android」

如果只想在自己的手機上像 App 一樣用，實際上有三層問題要先分開：

### 1. 產品層

先確認你每天真正怎麼用它：

- 怎麼打開
- 怎麼開始今天訓練
- 怎麼快速輸入每組資料
- 怎麼看上次紀錄
- 怎麼結束並保存
- 怎麼回頭看歷史

如果這條主流程沒先定清楚，就算包成 APK，也只是把現在的問題搬進 App 殼裡。

### 2. Web App 層

現在這個工具本質上是瀏覽器裡跑的程式。

先把它整理成：

- 更穩定
- 更好維護
- 更適合手機
- 更適合長期迭代

這一步通常比 Android 本身更重要。

### 3. Android 容器層

只有在你確認「Web 版流程本身已經合理」之後，才需要決定：

- 只做 PWA 就夠
- 還是要再包成 Android App

---

## 建議採用的兩段式策略

### 第一段：先做到「像 App」

目標：

- 從手機桌面點開
- 畫面像 App，不像普通網站
- 可離線使用
- 訓練資料不容易丟
- 進出 App 體驗穩定

這一段的核心不是 Android SDK，而是把現有專案升級成比較完整的手機 Web App。

### 第二段：如果還不夠，再做成 Android App

只有當你發現以下問題時，再考慮進 Android 容器：

- 手機安裝感不夠完整
- 檔案匯入匯出受限
- 想要更像本機 App 的操作方式
- 想控制啟動畫面、圖示、權限、檔案行為

這時再做 APK，成本才合理。

## 中長期產品擴張方向

參考 `AppearanceLab` 的設計思路，這個專案未來不一定只停在健身訓練記錄。

長期可以擴成三層產品：

```text
Layer 1
  健身訓練 App
  - 課表
  - 訓練記錄
  - 歷史與表現

Layer 2
  體態追蹤
  - 體重 / 體脂 / 腰圍
  - 月度體態照片
  - 身體變化趨勢

Layer 3
  外觀與風格實驗
  - 穿搭
  - 髮型
  - 眼鏡
  - 外觀月報
```

但這個順序不能反過來。

目前合理做法仍然是：

1. 先把訓練記錄主流程做穩
2. 再接上身體指標與體態追蹤
3. 最後才擴到穿搭 / 髮型 / 眼鏡等外觀實驗功能

## 流程架構圖

### A. 現況

```text
你
  ↓
手機瀏覽器
  ↓
開啟 workout_logger.html
  ↓
匯入 train_log.md
  ↓
訓練中記錄組數 / 重量 / 次數 / 休息
  ↓
匯出新的 markdown 紀錄
```

問題是：

- 啟動方式像檔案或網頁，不像 App
- 資料與檔案流轉比較手動
- 專案結構不利於長期擴充

### B. 目標狀態

```text
你
  ↓
手機桌面 App 圖示
  ↓
打開「健身 App」
  ↓
直接進入今日訓練
  ↓
快速記錄組數 / 重量 / 次數 / 休息
  ↓
自動保存
  ↓
可查看歷史、分析、月報
```

差異不只是包裝，而是整個使用流程更連續。

## 分階段任務地圖

### Phase 0: 釐清方向

這一階段先不寫功能，先定義：

- 這個 App 的第一版要保留哪些功能
- 哪些功能是現在就需要
- 哪些功能只是想像中很酷，但目前不必要

你現在最核心的功能大概只有：

- 今日課表
- 訓練記錄
- 上次數據參考
- 訓練完成保存
- 歷史紀錄查看

### Phase 1: 整理現有工具

目標是讓它從「單一 HTML 檔」變成比較穩定的 App 基底。

要處理的概念包括：

- 拆分結構、樣式、邏輯
- 整理資料模型
- 釐清儲存格式
- 讓手機操作更穩定

這一步完成後，你還是 Web，但已經不是臨時工具狀態。

### Phase 2: 變成可安裝的手機版

這階段的關鍵是：

- 可以加到主畫面
- 可以像 App 一樣啟動
- 支援離線
- 有 icon、名稱、啟動畫面

如果做到這裡你已經滿意，可能根本不需要 Android 原生殼。

### Phase 3: 必要時再包 Android 容器

只有在 Phase 2 仍不足時，才做這一步。

目的不是重寫，而是：

- 用 Android 殼裝現有前端
- 補足檔案操作或啟動體驗
- 安裝成 APK 到你自己的手機

### Phase 4: 長期優化

等你真的每天都在用後，再決定是否要做：

- 更完整的首頁
- 更好的歷史搜尋
- 更強的分析頁
- 備份 / 還原
- 雲端同步

## 可能的實作路線比較

### 路線 A：只做 PWA / 安裝型 Web App

你可以理解成：

- 還是 Web 技術
- 但看起來更像 App
- 可從手機主畫面開啟

優點：

- 開發成本最低
- 最接近你現在的基礎
- 不需要立刻學 Android

缺點：

- 某些檔案行為與系統整合能力有限
- 有些地方仍有瀏覽器感

適合你現在作為第一優先考慮。

### 路線 B：Web App + Android 包裝

你可以理解成：

- 核心還是現在這套前端
- 但外面包一層 Android App 外殼

優點：

- 安裝感更完整
- 可以生成 APK
- 更像真正 App

缺點：

- 需要碰 Android Studio
- 維護層次變多一層

這通常是第二步，不是第一步。

### 路線 C：重寫成原生或跨平台 App

例如：

- Kotlin Android
- Flutter

優點：

- 長期最完整
- 最像正式產品

缺點：

- 重新學習成本最高
- 幾乎等於重做

以你現在的目標來說太早。

---

## 你接下來真正要做的決策

不是決定「要不要學 Android」，
而是先決定以下幾件事：

### 決策 1：第一版 App 的最小功能是什麼

建議第一版只保留：

- 今日訓練
- 記錄組數
- 自動保存
- 歷史紀錄

### 決策 2：資料還要不要依賴 markdown 匯入匯出

這是很大的分水嶺。

如果未來想更像 App，通常會慢慢從：

- 手動匯入 / 匯出 markdown

轉向：

- App 內本地資料保存
- 有需要時再匯出備份

### 決策 3：你的近期目標是「能用」還是「漂亮完整」

如果近期目標是能用，就應該優先：

- 先穩定流程
- 再補外觀與架構

---

## 建議的最終方向

以你目前的背景與目標，我建議優先走這條：

```text
現有單檔工具
  ↓
整理成較乾淨的 Web App
  ↓
做成可安裝、可離線、像 App 的版本
  ↓
先在自己的手機上長期使用
  ↓
確認哪些地方真的不夠
  ↓
必要時再包成 Android APK
```

這樣的好處是：

- 風險最低
- 最貼近你現在已有成果
- 不會一開始就被 Android 學習曲線拖住
- 每一步都能保留現有可用功能

---

## 目前不建議做的事

在方向還沒完全清楚前，不建議立刻做：

- 直接重寫成 Kotlin App
- 直接做後端
- 直接做帳號登入
- 直接把功能大幅擴張
- 直接追求上架規格

這些都會讓專案複雜度暴增，但不一定提升你每天訓練時的實際體驗。

---

## 下一步討論建議

接下來最值得先討論的不是技術，而是「你的理想使用流程」。

也就是把下面這條路徑定清楚：

```text
打開 App
  → 看到什麼
  → 點哪裡開始訓練
  → 怎麼記錄最順
  → 訓練結束後怎麼保存
  → 之後怎麼回頭看紀錄
```

只要這條流程定清楚，之後不論是做 PWA 還是 Android 包裝，決策都會容易很多。
