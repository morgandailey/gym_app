# Known Issues

## 這份文件的目的

這份文件用來整理目前專案中已知、可疑、或高機率存在的問題。

它的用途不是直接修 bug，而是先回答這個問題：

> 目前這個系統哪些地方可能出錯？哪些問題已經看得出來？哪些地方最值得優先驗證？

## 這份文件適合什麼時候看

當你要做下面這些事情時，應該先看這份：

- 排修 bug 優先順序
- 討論哪些功能暫時不要動
- 規劃測試清單
- 決定哪些邏輯需要重寫

## 這份文件和其他文件的關係

- 上層入口： [README.md](./README.md)
- 現況總覽： [CURRENT_STATE.md](./CURRENT_STATE.md)
- 方向規劃： [APP_TRANSITION_PLAN.md](./APP_TRANSITION_PLAN.md)
- 這份文件角色：負責「問題盤點」

## 一句話總結

目前這個專案最大的風險不是單一明顯錯誤，而是：

- 多個資料來源並存
- 動作名稱映射複雜
- 很多功能依賴 markdown regex
- UI 狀態更新靠手動控制

所以它的 bug 很可能是「平常看起來沒事，但特定操作順序會壞」。

---

## 問題分類

這份文件把問題分成三類：

- `已知問題`
  - 幾乎可以確認有風險或已經看得出邏輯不穩
- `高風險可疑區`
  - 還沒逐項驗證，但非常容易藏 bug
- `產品層問題`
  - 不一定是程式 bug，但會影響體驗與未來方向

---

## 已知問題

### 1. 休息時間可能遺失

目前 rest timer 只會在特定時機把休息時間寫回上一組。

高風險情境：

- 做完一組後切到別的動作
- 做完一組後直接結束訓練
- 做完一組後清空當日資料
- 做完一組後刪除某組

可能結果：

- 休息秒數沒有被保存
- 保存到錯的組
- UI 與實際資料不一致

影響層級：高

---

### 2. 動作主名稱與變體名稱可能不一致

目前像「臥推」這種主名稱只是 UI 容器，實際紀錄常常是用變體名稱存。

例如：

- `臥推`
- `槓鈴臥推 (Barbell Bench Press)`
- `啞鈴臥推 (Dumbbell Bench Press)`

可能結果：

- 上次紀錄抓錯
- 同類動作切換後顯示異常
- 分析漏算
- PR 歷史不完整

影響層級：高

---

### 3. 分析功能依賴動作命名完全一致

分析邏輯是根據 `MUSCLE_SCORES`、`ANTAG`、`INTRA` 等規則表來判斷。

如果名稱不一致，會直接造成：

- 肌群分析缺資料
- 比例分析不顯示
- 某些動作被當成不存在

這個問題不是畫面 bug，而是資料映射 bug。

影響層級：高

---

### 4. 自訂動作可以記，但分析不一定認得

目前自訂動作系統和分析系統不是完全整合。

可能結果：

- 訓練中能輸入
- 匯出後 markdown 有紀錄
- 但分析頁、PR、月報不一定正確反映

影響層級：中到高

---

### 5. `logMd` 和訓練暫存 state 是兩套世界

目前系統同時有：

- `sets`：正在練的暫存資料
- `logMd`：歷史文字資料

這兩者不是統一資料模型。

可能結果：

- 某些資料已寫入 state 但沒進歷史
- 某些資料已進歷史，但 UI 還停留在舊狀態
- 清除與重載流程容易有遺漏

影響層級：高

---

### 6. Markdown 是核心資料格式，但格式很脆弱

目前很多功能都依賴 regex 去解析 markdown。

只要這些條件改變，就可能壞掉：

- 日期格式
- 欄位數
- 單位文字
- 破折號表示法
- 空白與換行

可能結果：

- 匯入成功但解析不完整
- 分析為空
- PR 圖沒資料
- 月報統計錯誤

影響層級：高

---

### 7. panel 切換狀態靠手動控制，容易不同步

目前日誌、分析、月報、GitHub 面板切換都靠手動 `display` 與按鈕文字切換。

可能結果：

- 實際面板已關，但按鈕還顯示「關閉」
- 某些 panel 沒有正確關掉
- 某些資料應該重 render 卻沒發生

影響層級：中

---

### 8. GitHub 同步功能混入主產品流程

GitHub 區塊實際上是開發維護功能，不是健身產品功能。

可能問題：

- 增加 UI 複雜度
- 增加資料與權限風險
- 分散主流程注意力

影響層級：中

---

## 高風險可疑區

這些地方目前不一定已經確認壞掉，但很值得列為測試重點。

### 1. 同一個動作在不同 day 重複出現

例如：

- `啞鈴側平舉`
- `Hanging Leg Raise`
- `面拉 (Face Pull)`
- `二頭` 相關變體

需要確認：

- 上次資料是否抓對
- PR 是否合併正確
- 分析是否重複或漏算

---

### 2. 刪除某組後的休息資料與組號是否還正確

目前每組休息資料綁在陣列 index 上。

如果中間刪組，可能需要驗證：

- 後續組數顯示是否正確
- rest 是否還跟正確的組對應

---

### 3. 切換 `kg / lb` 後輸入與顯示是否完全一致

目前有：

- 顯示單位
- 輸入單位
- placeholder 單位
- markdown 匯出單位

需要確認：

- 轉換後是否有四捨五入誤差累積
- placeholder 與實際提交值是否一致
- 自訂動作與原生動作的單位邏輯是否一致

---

### 4. 訓練完成後立刻重新開始新的一天

需要驗證：

- `finishedDays` 是否正確
- `sets` 是否真的清空
- `logMd` 是否更新
- tab 狀態是否同步

---

### 5. 清除快取與清除日誌之後的狀態殘留

目前有多種清除操作：

- 清除當日
- 清除載入日誌
- 清除所有暫存

需要確認：

- 是否真的全部清乾淨
- 是否有 UI 還保留舊資料
- 是否有分析面板殘留舊結果

---

### 6. 匯入不同格式或舊版日誌

需要確認：

- 匯入後是否部分功能仍可用
- 哪些功能會直接失效
- 錯誤是否有被看見

目前看起來，這一塊很可能是 silent failure。

---

### 7. 自由日與自訂動作混用情境

需要驗證：

- 自由日只靠自訂動作時是否穩定
- 非自由日加入很多自訂動作時是否正常
- 自訂動作與課表既有動作同名時是否有衝突

---

### 8. PR 下拉選單與變體動作的對應

目前 PR 選單有依課表與歷史資料分組。

需要確認：

- 變體動作是否會漏掉
- 主名稱與變體是否重複或錯分
- 課表中沒有、但歷史中有的動作是否穩定顯示

---

## 產品層問題

這些不一定是程式錯誤，但會影響後續方向。

### 1. 主流程過度依賴匯入 markdown

目前如果沒有先匯入 log，很多參考資料與分析能力都會變弱。

這代表產品體驗很依賴外部檔案流程，而不是 App 自身狀態。

---

### 2. 訓練資料與歷史資料還不是統一模型

這會讓未來要做 App 化、本地保存、資料同步時很難直接延用。

---

### 3. GitHub Sync 對最終產品目標不一定必要

它對現在開發可能有用，但對未來手機 App 主流程不一定重要。

---

### 4. 功能很多，但優先順序尚未清楚

目前系統已經有：

- 訓練記錄
- 日誌
- 分析
- 月報
- GitHub

但還沒有明確定義：

- 哪些是 MVP 核心
- 哪些只是輔助功能
- 哪些應該延後

---

## 建議的問題處理順序

如果之後要開始修，不建議隨機修。

比較合理的順序是：

1. 先驗證主流程資料正確性
2. 再處理動作名稱 / 變體映射
3. 再處理 rest timer 與 state 同步
4. 再檢查 markdown 解析穩定性
5. 最後才整理分析與附加面板

理由很簡單：

- 主流程錯，其他功能都沒有意義
- 資料模型錯，分析結果再漂亮也不可信

---

## 目前最值得優先驗證的測試路徑

下面這幾條建議未來優先實測：

### 路徑 1：標準訓練流程

```text
匯入舊 log
  → 開始 Day 1
  → 記數組
  → 自動 rest
  → 完成訓練
  → 匯出
  → 重新匯入
  → 檢查資料是否一致
```

### 路徑 2：變體切換流程

```text
同一天中切換某個動作的 variant
  → 記錄數組
  → 完成訓練
  → 檢查上次資料、分析、PR 是否正常
```

### 路徑 3：自訂動作流程

```text
新增自訂動作
  → 記錄數組
  → 匯出 / 重新匯入
  → 檢查是否正確顯示與保存
```

### 路徑 4：中途中斷流程

```text
記一組
  → rest 計時中
  → 切到別的動作 / 清除當日 / 結束訓練
  → 檢查 rest 是否正確處理
```
